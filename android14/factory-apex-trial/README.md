# Android 14 factory APEX activation on SM-T700

Trial 26 uses the installed Android 14 apexd on Linux 6.12.118. It activates the 31 factory packages listed in [the installed inventory](installed-modules.txt) and runs init's standard APEX configuration in the default mount namespace. The trial mounts a 128 MiB tmpfs at /data for APEX session and runtime directories. Internal MMC stays read-only.

## Build and validation

1. Reuse the first-stage init, cgroup inputs, embedded bootconfig, stock SELinux policy and read-only MMC guard from trial 25. Package [klimt-factory.rc](klimt-factory.rc) as `/klimt-property.rc` in the embedded ramdisk. Keep the first-stage init copy into tmpfs under /dev. [Prior diagnostic](../binder-ipc-trial/README.md)
2. Replace the prior SELinux entry header with [factory-entry.h](factory-entry.h). Keep the kernel hooks for policy commit and userspace kmsg. Use a fresh 16-digit hexadecimal run ID in the decompressor records, embedded bootconfig and ramdisk. Set `androidboot.init_rc=/dev/klimt-property.rc`, `androidboot.klimt_factory=1` and `g_serial.iSerialNumber=SMT700-FACTORY` on the tablet.
3. The RAM script uses the factory bootstrap APEX setup and starts the installed service manager on framework Binder. After Binder readiness it switches init to the default mount namespace. Before launching apexd, the kernel checks for a distinct namespace, writable tmpfs /data and 31 absent package manifests. The script starts the regular apexd with its stock capabilities, waits for `apexd.status=activated`, and calls `perform_apex_config`. The isolated trial uses the stock fallback for the absent vold service and stores the session directory in tmpfs.
4. The end marker is checked in PID 1's mount namespace. Every unversioned manifest must be visible on a separate read-only ext4 loop device. The probe also checks the active package list file, the newly generated linker configuration, the writable tmpfs and apexd's enforcing SELinux domain and mount namespace. User-space next steps such as `apexd --snapshotde` and framework startup are outside this activation checkpoint.
5. Run [verify-factory-log.py](verify-factory-log.py) with the matching run ID on the USB capture and the retained console. The verifier compares source paths, package names and versions from apexd's mount logs with the installed inventory and checks all 31 distinct loop devices. The recovery restart follows the verdict, and a separate kernel deadline can restart if init stalls.

For the ARM QEMU negative control, use the same kernel, ramdisk and installed SYSTEM snapshot with `androidboot.klimt_factory=0`. The bootstrap and temporary data setup still run. The regular apexd is skipped and the probe checks a second time that all 31 paths are absent before requesting recovery. Use `--negative` with the verifier.
