# Android 14 SDK extensions and ART classpath on SM-T700

Trial 27 checks the installed Android 14 `derive_sdk` and `derive_classpath` services on Linux 6.12.118. It retains the factory APEX and temporary RAM data setup from trial 26. The expected outputs are Android API 34 with extension version 11 for R, S, T, U and Ad Services, and a 3,887-byte classpath export file. [Factory APEX trial](../factory-apex-trial/README.md)

## Building and verifying

1. Reuse the previous first-stage init, cgroup data, embedded bootconfig, stock SELinux policy, hardware DTB and read-only MMC guard. Package [klimt-classpath.rc](klimt-classpath.rc) as `/klimt-property.rc` in the embedded ramdisk. First stage stages it under /dev. Use a fresh matching 16-digit hexadecimal run ID in the decompressor records, ramdisk and bootconfig.
2. Copy the preceding [factory entry header](../factory-apex-trial/factory-entry.h) to `classpath-entry.h` and apply [classpath-entry.patch](classpath-entry.patch) from its containing directory with `patch -p1`. Install the resulting header as the instrumented SELinux entry probe. Select `androidboot.init_rc=/dev/klimt-property.rc`, `androidboot.klimt_classpath=1` and `g_serial.iSerialNumber=SMT700-CLASSPATH`.
3. Run the boot through normal activation of all 31 APEXes. `perform_apex_config` imports both services directly from the installed SDK Extensions APEX. The diagnostic checks for a clean RAM data mount, initializes the needed `/data/system/environ` directory with the installed SELinux labels and runs both one-shot services with their shipped identities.
4. Init loads the exports file with `load_exports`. A separate UID 2000 shell reconstructs the four export lines solely from its inherited environment and reports their SHA-256 through a temporary property. The kernel checks that the file resides on tmpfs, validates each JAR path and compares the file hash with the shell's. The host independently reconstructed the same file from the 38 shipped classpath protobuf fragments, filtering by API level 34 in the order defined by derive_classpath. The final byte count, 39/14/13/7 path counts and digest must match that reconstruction.
5. Run [verify-classpath-log.py](verify-classpath-log.py) with the matching run ID on live USB ACM and the retained kernel console. This checks the service import order, exit statuses, fresh SDK properties, generated file and the child environment. For the ARM QEMU negative control, set `androidboot.klimt_classpath=0` and pass `--negative` to the verifier. SDK derivation still runs, and the classpath file must remain absent before the software recovery reboot.

This checkpoint verifies the configuration used by ART. Running ART boot helpers, generating boot artifacts and launching Zygote are later checkpoints.
