# Android 14 APEX bootstrap on SM-T700

Trial 24 runs the installed ARM32 `/system/bin/apexd --bootstrap` and init's `perform_apex_config --bootstrap` on the read-only SYSTEM used in trial 23. The three targets on this installed image are `com.android.runtime@1`, `com.android.i18n@1` and `com.android.tzdata@350090000`. The target list comes from the installed package manifests and the factory bootstrap selection in Android's apexd. ART is present on SYSTEM and belongs to a later activation stage.

## Building and running the probe

1. Retain the previous static first-stage init, cgroup files, stock SELinux policy, hardware DTB and read-only MMC guard. Package [klimt-apex.rc](klimt-apex.rc) as `/klimt-property.rc` in the embedded RAM disk. First stage copies it into tmpfs before switching root. [Prior image assembly](../ueventd-coldboot-trial/README.md)
2. Replace the trial 23 probe at `security/selinux/policy-entry.h` with [apex-entry.h](apex-entry.h). Keep the printk and policy-commit instrumentation from the preceding diagnostic patches. Generate a fresh 16-digit hexadecimal run ID for both decompressor records, bootconfig and ramdisk. The tablet command line selects `androidboot.init_rc=/dev/klimt-property.rc`, `androidboot.klimt_apex=1` and `g_serial.iSerialNumber=SMT700-APEX`. Use built-in loop, ext4 and device mapper support.
3. The RAM script prepares the bootstrap linker directory, starts ueventd, runs the one-shot bootstrap service synchronously as root with group system and capability SYS_ADMIN, and calls the native init builtin. The stock service's bootloader-on-failure directive is omitted in this diagnostic so that a bootstrap error can be captured and the independent kernel timer can request recovery. These early actions run with the installed enforcing policy. No writable userdata mount is needed.
4. Capture the diagnostic ACM stream on the target port. Compare it with the previous kernel console after automatic TWRP return. Match the fresh run ID, PID in the apexd domain, each versioned mount, the three unversioned manifest paths on distinct read-only loop devices, service exit status, generated linker configuration and final software restart.

The kernel checks paths in PID 1's mount namespace before the service and again after the native coldboot barrier. Before startup it requires three absent manifests and the stock one-byte linker placeholder. After startup the manifests must be regular files with the installed payload sizes on read-only block-backed ext4. It also checks for a larger configuration on tmpfs and init's own successful linker generation message. A kernel workqueue requests recovery after the verdict, with an independent 70-second deadline if init stalls.

For the ARM QEMU negative control, use the same kernel, ramdisk and installed SYSTEM snapshot with `androidboot.klimt_apex=0`. Ueventd still completes. The conditional bootstrap and configuration commands are skipped, all three paths stay absent, the linker file stays at one byte and the probe must report FAIL before the recovery reboot. The positive control must additionally show the three expected versioned APEXes mounted from SYSTEM and a normal service exit with status 0.
